# Strategy live checkout: operations and limits

This code can create real AED 1,200 Ziina payment intents only when `STRATEGY_EXPERIMENTAL=true`, `STRATEGY_MODE=live`, and `STRATEGY_LIVE_ENABLED=true`, with all other strategy server settings valid. Live is off by default. The free 20-minute call is unchanged. Existing test rows are not live rows; test and live browser cookies, API routes, queries and scheduler flags are separated. No provider calls are made merely by enabling the setting until a visitor submits checkout. Backend mock tests are not proof the real account, host, webhook, cron, support or refund processes work.

## Before opening checkout

- Confirm privately that the Ziina key belongs to the intended business and can create real AED payment intents. An account ID, if set, is checked against creation and each subsequent lookup; if omitted, binding only proves consistency, not business ownership.
- Confirm the Google appointment form requires the exact `Booking reference` question, is for the intended calendar and the reference appears in the calendar event; one real test matched, but format changes need monitoring. A reference is not identity. Anyone given the Google appointment URL could share it or book without paying, so match status is not a secure access-control system.
- Confirm a real person monitors the contact channels and private records, handles missing bookings and fulfils the advertised cancellation/refund policy. The consultation-choice card currently says the payment link is sent after booking, while this checkout charges before booking; the copy should be resolved with the owner before public launch.
- Confirm RLS, database backups, server-only secrets, reliable Google OAuth refresh, Hostinger process capacity, and who monitors cron failures. The scheduler is not a durable queue and has no automated alerts.
- Ziina documents one webhook URL per account. Do not change or overwrite any existing webhook without reviewing its use. The live workflow here does not process Ziina webhooks or automatically synchronize refunds. The existing test-only webhook route returns unavailable in live mode; if it was registered, it will no longer process test events while live mode is selected. The live cron is mandatory for unattended payment recovery and booking matching.

## Configuration

In the website's private server environment keep the existing `Z_A_KEY` (or single matching key alias), `ZIINA_WEBHOOK_SECRET`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `STRATEGY_ORIGIN`, `BOOKING_STRATEGY_EMBED` and Google Calendar variables. `ZIINA_WEBHOOK_SECRET` is currently required for configuration compatibility even when not using a webhook. Set `STRATEGY_EXPERIMENTAL=true`, `STRATEGY_MODE=live`, `STRATEGY_LIVE_ENABLED=true`. These flags enable real charges after deployment. `VITE_STRATEGY_TEST_UI` is not needed for live and can be disabled; if removed it requires a frontend rebuild. Never put a secret in a `VITE_` variable or cron command.

Configure exactly one Hostinger live scheduler with `STRATEGY_AUTO_MATCH_LIVE=true`, `STRATEGY_MODE=live`, `STRATEGY_LIVE_ENABLED=true`, the existing private env file and `scripts/auto-match-strategy-live.cjs`, every 10 minutes. Hostinger cron may not inherit the website's settings; use the private env file and explicit non-secret overrides with `env` before Node. Node's existing process environment takes precedence over `--env-file`. Preserve the actual paths and Node version from the working test cron. Disable the old test job when switching; do not run both as additional processes without considering Hostinger capacity. Verify private cron output and account for timezone. Never print the env file.

## Operations

- A successful customer return checks Ziina itself and exposes the booking form only for the same bound payment intent/account, amount and currency. If the browser never returns, the live cron rechecks up to 10 bound pending attempts per run; it rotates checked rows to avoid persistent starvation. Unbound intents, database failures and disabled/failed jobs still need manual reconciliation. Counts do not prove every payment has been recorded.
- The job checks up to 10 paid unmatched rows per run, scanning confirmed Google events within seven days before to 90 days after the run. It verifies Ziina again and links only a unique supported reference; otherwise the row remains unmatched and may require private review. Booking cancellations and reschedules are not synchronized. No match is not proof that there is no booking. Rows/attempts are never automatically cancelled and no unsolicited outreach is performed.
- A visitor who returns to the strategy checkout using the same browser and still-valid secure session cookie is checked automatically; a freshly verified payment reopens the reference and booking form. The cookie expires after seven days; a different browser/device, cleared cookies or an expired session needs team help. Google form fields already typed are not restored by our site. An IP address is not used as identity.
- If a customer contacts the team after a payment or booking problem: do not ask for card numbers, CVV or passwords, and do not ask them to pay again. Privately inspect the matching row and Ziina payment using the bound intent ID, amount, currency and business account, and check the calendar before taking action. Name, WhatsApp or a reference alone is not proof of identity. Verify the requester by an appropriate independent channel before sharing appointment/payment details or granting access.
- Refunds are manual and must be verified in Ziina; this software neither issues refunds nor keeps their state synchronized from Ziina. Before initiating one, privately mark the matching row `refund_review` using a reviewed conditional update, which prevents further access through this checkout; after confirming a full refund, record `refunded`. A shared Google URL already shown to a visitor cannot be revoked by this status. Partial/failed/pending refunds require review; do not guess. Only an authorized operator should modify payment states. Do not delete records to handle refunds.
- For urgent stop, set `STRATEGY_LIVE_ENABLED=false` in the website environment and redeploy/restart, then disable the live cron. This prevents new checkout and also disables browser status access for existing customers, so handle pending customers manually. It does not cancel existing Ziina intents or appointments.
