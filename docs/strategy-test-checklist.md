# Strategy booking: private test checklist

This is an unfinished, test-only integration, not approval for live payments. The public website keeps its coming-soon screen. Never paste keys, tokens, customer records or raw provider responses into chat or logs. Private staging is preferable. The owner has approved a temporary team-only test on the live host when staging is unavailable; this still cannot protect against every hosting or operational risk.

A separate test page at `/?strategy-test=1` is available only when the frontend is built with `VITE_STRATEGY_TEST_UI=true`. The test backend also requires a distinct, random server-only `STRATEGY_TEST_PASSWORD` of at least 32 characters. The page requires this password, and every checkout/status API request requires the signed one-hour Secure, HttpOnly access cookie; missing settings fail closed. The password and service keys must never use a VITE_ name. The gate is a temporary shared team credential, not a production identity system; its in-memory rate limiter is not distributed. Keep the password private, test only with consented team data, and remove the test settings after the test. Verify from a fresh browser that checkout APIs reject unauthenticated requests and the public popup remains coming-soon. A test-payment cookie lasts seven days; if it is lost or a request is interrupted, manual review is needed.

Verify that the initial table and grant already created manually match the migrations. Review and apply the separate customer-name and Ziina account-column migrations; do not re-run an initial migration blindly or delete existing records. Old attempts lacking a bound account must be reviewed, not automatically completed. Review access, backups and retention. Do not create a webhook on the existing Ziina account until its current configuration is checked and the owner approves: Ziina documents that registering a new URL overwrites the previous one. A signing secret is still required by the current test configuration even without registration.

The server independently requires its explicit test configuration and always sends Ziina `test: true`; it rejects live mode. Do not assume test/live isolation based on that alone: confirm actual Ziina account behavior, response fields and redirect host. Real provider requests, interrupted checkout, timeouts, duplicate payments, refunds, recovery and webhook edge/IP handling have not been verified.

For the calendar investigation, make a single consented test appointment in the actual intended test schedule. If the booking form supports a required custom reference, enter a unique lowercase 32-character hexadecimal test reference. From a private trusted process with the four Google environment settings already available, an operator can run:

```text
node scripts/check-strategy-calendar.cjs START_ISO END_ISO TEST_REFERENCE
```

Replace all three arguments locally with a time window of at most 31 days around the test event and the test reference. The diagnostic does not change the database or show event details: it reports the number of events containing the exact reference in description or extended properties, and whether a matching event has an attendee email/start time. A count of zero, multiple matches, an empty email, inaccessible fields or any error must be reviewed, not interpreted as a customer not booking. An attendee email is not automatically proven to be the customer's. The script is not a public endpoint, scheduler, reconciliation worker, or proof that the booking form's custom answers are supported long-term. Do not log raw events or real client details during testing.

A test-only matching module can update the same paid test row when a single confirmed event contains a plain-text `Booking reference: <reference>` line. An explicitly enabled `STRATEGY_MATCH_TEST_ONLY=true` team-only button checks only the authenticated paid test session, scanning seven days before to ninety days after the check. It never runs automatically or touches live rows, and this event format has not been verified with Google. The operator-only `scripts/match-strategy-test.cjs` also requires explicit test-mode settings and an `--apply` argument. Do not assume a missing match means no booking. Before enabling a test write, review the diagnostic and real event format. Before launch, verify the format and implement and review reliable production matching, cancellation/rescheduling, duplicate and unmatched reference handling, and manual team review; never equate a missing match with proof of no booking. Build session recovery and reliable payment reconciliation and refund handling; handle webhook allowlisting safely at the hosting edge. The payment link and calendar URL can be shared; a booking reference is for matching, not a security barrier. Obtain owner approval and complete real-provider staging and operational tests before any controlled live transaction.
