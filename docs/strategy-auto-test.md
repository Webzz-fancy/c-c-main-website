# Scheduled automatic matching — protected test only

The external scheduler runs `scripts/auto-match-strategy-test.cjs`. It runs independently of the browser and exits; the website process does not spawn workers, timers or cron jobs. Nothing runs until both the private server configuration and the host scheduler are enabled. This is not a production implementation and is not approval to accept real payments.

1. Confirm the existing protected Ziina test and Google Calendar settings work, the customer-name/account columns and table permissions are present, and the real test appointment reference has been successfully matched manually. Keep the settings server-only.
2. Privately add `STRATEGY_AUTO_MATCH_TEST=true` in the Node.js site's Hostinger environment settings, alongside the existing `STRATEGY_EXPERIMENTAL=true` and `STRATEGY_MODE=test`. Redeploy if the host requires it. Do not set this in any `VITE_` variable. This flag is read by the scheduled script, not by the web process, so it does not start a background task.
3. In Hostinger, create a **Node.js** Cron Job under the site's Advanced → Cron Jobs, using the actual Node version, account username, environment-file path and deployed script path shown in the Hostinger panel. Schedule it every 10 minutes. Hostinger says Node.js cron jobs do **not** automatically inherit the website environment, so configure the `--env-file` option as described by Hostinger. Node's `--env-file` needs Node 20.6+; for Node 18, use a separately reviewed private environment-loading method or select a compatible version. Never paste environment values into the job command, logs, browser code, Git or chat. Do not assume the example Hostinger path is the correct path for this account.
4. Confirm the job's private output reports a successful run and test with the existing unmatched paid test appointment. Verify the same row and event in Supabase/Google. No new test payment is required to exercise a previously unmatched recent test row. Do not expose references, customer data, provider details or secrets in screenshots. On early failure, the job emits only a fixed reason code (for example `auto_flag_not_enabled`, `supabase_settings_missing`, `database_read_failed`, or `calendar_authorization_failed`); these categories contain no secret values. The code identifies a step, not the exact underlying provider error. If a flag or setting is reported missing despite being in hPanel, verify the cron is loading the correct environment file and redeployed settings. Do not print environment variables to troubleshoot.
5. Stop/remove the cron and set the flag to `false` after testing. Monitor the host's process allowance; this is a short-lived scheduled process, not a permanently running worker, but it still consumes resources when running. A successful cron exit/HTTP 200 is not proof that every booking matched.

The job first rechecks recently created (last seven days) pending **test** payments with a bound intent and account, at most 10. It independently checks Ziina and conditionally updates that same row to completed only if the stored intent and account, amount and currency match and Ziina reports completion. Unbound attempts, older attempts, refund events, failed status handling and lost browser sessions still require manual review. It then scans recent completed, unmatched **test** rows (at most 10) and confirmed events between seven days before and ninety days after the run. If the pending batch exceeds the limit, no payments are recovered in that run, an error is reported, and the separate booking-matching stage is still attempted. If the booking batch exceeds its limit, that stage fails closed; payment recovery performed before a later booking-stage failure remains saved. All calendar pages (max 10, up to 100 items each) are fetched before any booking match is written. A unique supported visible reference is required, and the same guarded test row is updated; ambiguous or unfamiliar events remain unmatched. The job reports only aggregate counts. A row left `not_booked` is not proof there was no appointment. API failures, expired Google authorization, job failure, downtime, appointments outside the window, test attempts older than seven days, batches over 10 records, or repeated process limits require private review. The next run retries eligible rows, but there is no alerting, durable queue, cross-instance lock, long-term reconciliation, cancellation/reschedule sync, refunds, verified customer email, or production recovery system. A reference links records, not identity. A shared Google booking link can bypass checkout.

The host reports one-day temporary extra process capacity; verify a durable resource solution. Do not enable live payments or claim automatic production reconciliation on the basis of this test.
